## 1. Tech Stack

### Languages & Runtime
- **TypeScript** (strict, v5.9) — entire codebase
- **Node.js** — local dev; Cloudflare Workers — production

### Database
- **PostgreSQL** via **Neon** (serverless/edge-compatible)
- Prisma manages schema and migrations (`prisma/schema.prisma`)
- At runtime, queries use raw `@neondatabase/serverless` Pool — NOT the Prisma ORM client — because the Cloudflare Workers runtime does not support Node TCP sockets
- Prisma client is generated to `lib/generated/prisma/` with `runtime = "cloudflare"` but the application data layer (`lib/db.ts`, `lib/server/*.ts`) uses parameterized SQL directly via the Neon pool

### Build & Deploy
- `npm run build` — standard Next.js webpack build
- `npm run cf:build` (`opennextjs-cloudflare build`) + `wrangler deploy` — Cloudflare production
- `prisma generate` runs as `prebuild` and `postinstall` hooks

### Key Config Files
- `prisma/schema.prisma` — canonical data model
- `next.config.ts` — Next.js config
- `open-next.config.ts` — OpenNext/Cloudflare adapter config
- `wrangler.jsonc` — Cloudflare Workers config
- `tsconfig.json` — TypeScript config with `@/` path alias for project root

## 2. Architecture

### Overall Pattern
Single-repo monolith: Next.js App Router application serving both the public mobile UI and the admin panel, deployed to Cloudflare Workers via OpenNext.

### App Structure

### Routing Model

**Public:**
- `/` — landing, defaults to first branch, `contact` tab; `?tab=menu` switches to menu
- `/b/[branchSlug]` — branch-specific URL (QR code target); same `PublicShell` component, different `basePath`

**Admin:**
- `/admin/login` — `.env` credential login
- `/admin` — dashboard + analytics summary
- `/admin/branches` — branch list + create/edit/toggle
- `/admin/categories` — category list + create/edit/toggle
- `/admin/products` — product list + create/edit/toggle/reorder
- `/admin/pricing` — pricing matrix, single-update and batch-update modes
- `/admin/branding` — business name, tagline, badge, SEO, brand colors

### Data Flow

**Public page render:**
1. Next.js RSC page (`app/page.tsx` or `app/b/[branchSlug]/page.tsx`) calls `lib/server/public-data.ts` functions
2. `public-data.ts` checks `hasDatabaseUrl()`: if true, runs raw SQL via `withDb()`; if false or on error, falls back to `lib/demo-data.ts`
3. Data passed as props to `PublicShell` component (server-rendered)
4. `AnalyticsBeacon` (client component) fires events to `/api/events` on mount via `navigator.sendBeacon`

**Admin write flow:**
1. Admin page submits HTML form to a Server Action (in `app/admin/*/actions.ts`) or to a REST API route handler
2. Server Action/route calls `requireAdmin()` to verify session cookie
3. Delegates to `lib/server/admin-data.ts` or `lib/server/pricing-data.ts`
4. These functions run parameterized SQL inside `withDb()` or `withTransaction()`
5. On success: Server Action redirects back with `?status=updated`; API routes return JSON

### Authentication
- Source of truth: `ADMIN_EMAIL` and `ADMIN_PASSWORD` environment variables
- Login route (`/api/admin/auth/login`) checks credentials, issues HMAC-SHA256 signed session cookie (`admin_session`, 12h TTL)
- `getAdminSession()` in `lib/auth.ts` reads and verifies the cookie on each request
- `requireAdmin()` in `lib/server/route-helpers.ts` wraps API route auth check
- Admin pages call `getAdminSession()` directly and `redirect("/admin/login")` if null
- `AdminUser` DB table exists in schema but is NOT used for authentication currently

### Demo/Fallback Mode
Every data function checks `hasDatabaseUrl()` first. Without `DATABASE_URL`, the entire app runs on static demo data from `lib/demo-data.ts` (3 Istanbul branches, 5 products). This is the "zero-config demo" mode referenced in the roadmap.

## 3. Key Features

### Built and Functional

**Public mobile UI:**
- Mobile-first single-page layout with sticky bottom tab bar (`İletişim` / `Menü`)
- Branch selector (horizontally scrollable pill buttons)
- Contact tab: branch cards with address, hours, Map/WhatsApp/Google Review action buttons
- Menu tab: category anchor navigation, product cards with image, price, stock status badges
- `EventLink` component wraps external links to fire analytics events (map_click, whatsapp_click)
- `AnalyticsBeacon` fires page_view, branch_view, tab_view on render

**Admin panel:**
- `.env`-based login with signed cookie session
- Dashboard with 5 KPI cards (total visits, top branch, call/map/WhatsApp clicks)
- Branch CRUD: create, update fields, toggle active/inactive
- Category CRUD: create, update, toggle active/inactive
- Product CRUD: create, update, delete, toggle active/inactive, reorder (up/down swap)
- Pricing matrix: filter by category/branch/search; single-product per-branch price+stock update; batch update (percentage / fixed delta / set fixed price)
- Branding editor: business name, tagline, badge, SEO title/description, primary/secondary/background colors

**Brand theming:**
- `Business` DB record stores 3 hex color fields
- `brandThemeToCssVariables()` maps them to `--brand-primary/secondary/background` CSS vars
- `PublicShell` applies theme as inline style, all derived UI tokens (`--accent`, `--card`, etc.) cascade from those three vars via `color-mix()`

**Analytics:**
- Anonymous session ID stored in `localStorage`
- Events written to `EventLog` table with `businessId`, optional `branchId`/`productId`, `sessionId`, `eventName`, `source`, `metadataJson`
- Dashboard summary aggregates page_view, call_click, map_click, whatsapp_click counts plus top branch by branch_view count

### Not Yet Built (per roadmap)
- Feedback form and moderation (Milestone 4 — Phase 4)
- Branch hours management in admin (field exists in schema, no admin UI)
- `branch_hours` CRUD
- `blurb` / `heroNote` branch fields — no admin edit UI (fields in schema and public display)
- Analytics API endpoint (`/api/admin/analytics/summary/route.ts` exists but admin dashboard fetches via server-side `getDashboardSummary()` directly)
- Per-product analytics (`menu_item_view` event type defined but no tracking UI)
- Role-based access control (schema has `AdminRole` enum, unused)
- Image upload/object storage (imageUrl is plain string input)
- Multi-language support

## 4. Database / Data Model

Schema at `prisma/schema.prisma`. Prisma generates types to `lib/generated/prisma/`. Runtime queries use raw SQL, not Prisma ORM methods.

### Core Tables

**`Business`** — single record, top-level tenant
- `id` (cuid), `name`, `slug` (unique), `logoUrl?`, `brandTagline?`, `brandBadge?`
- SEO: `seoTitle?`, `seoDescription?`
- Theme: `primaryColor?`, `secondaryColor?`, `backgroundColor?`
- Contact: `primaryPhone`, `primaryWhatsapp`, `defaultCurrency` (default: `TRY`)

**`Branch`** — physical locations
- `businessId` FK, `name`, `slug` (unique per business), `address`, `district`, `city`
- `phone`, `whatsapp`, `mapUrl`, `reviewUrl?`
- `latitude?`, `longitude?` (stored, not displayed yet)
- `isActive`, `displayOrder`, `blurb?`, `heroNote?`
- Has-many: `BranchHour`, `BranchProduct`, `Feedback`, `EventLog`

**`BranchHour`** — operating hours per day
- `branchId`, `dayOfWeek` (1=Mon, 7=Sun), `openTime?`, `closeTime?`, `isClosed`
- Unique on `(branchId, dayOfWeek)`

**`MenuCategory`** — groups products
- `businessId`, `name`, `slug` (unique per business), `description?`
- `displayOrder`, `isActive`

**`Product`** — core product identity (no price)
- `businessId`, `categoryId`, `name`, `slug` (unique per business)
- `description`, `imageUrl?`, `badgeLabel?`, `isFeatured`, `isActive`, `displayOrder`

**`BranchProduct`** — the critical join table: per-branch price + stock
- `(branchId, productId)` unique constraint
- `price` Decimal(10,2), `currency` (default: TRY)
- `stockStatus` enum: `in_stock | out_of_stock | hidden`
- `stockQuantity?` (optional numeric inventory)
- `isAvailable`, `displayOrderOverride?`, `isFeaturedOverride?`

**`Feedback`** — customer feedback (not yet surfaced in UI)
- `businessId`, `branchId?`, `rating?`, `message`, `source`
- `status` enum: `new | reviewed | archived`
- `contactName?`, `contactPhone?`

**`EventLog`** — analytics events
- `businessId`, `branchId?`, `productId?`, `sessionId`
- `eventName`, `source`, `metadataJson?`

**`AdminUser`** — future DB-based auth (schema only, not used for login)
- `businessId`, `email` (unique), `passwordHash?`, `authProviderId?`
- `role` enum: `owner | editor`, `isActive`, `lastLoginAt?`

### Key Indexes
- `Branch (businessId, isActive, displayOrder)`
- `MenuCategory (businessId, isActive, displayOrder)`
- `Product (businessId, categoryId, isActive, displayOrder)`
- `BranchProduct (branchId, productId)` unique + `(branchId, stockStatus)`
- `EventLog (businessId, eventName, createdAt)`
- `Feedback (businessId, status, createdAt)`

## 5. Notable Patterns & Conventions

### Demo/DB Duality Pattern
Every read function in `lib/server/` follows the same pattern:
```typescript
export async function getX() {
  if (!hasDatabaseUrl()) {
    return demoFallback;
  }
  try {
    return await withDb(async (db) => { /* raw SQL */ });
  } catch (error) {
    logFallback(error, "scope");
    return demoFallback;
  }
}
```
Write functions skip demo fallback and throw if no DB URL. This means the app is always demo-runnable without a database.

### Raw SQL Over ORM
All queries are hand-written parameterized SQL (`db.query<RowType>(sql, [params])`). Prisma is used only for schema definition and migration tooling. The generated Prisma client (`lib/generated/prisma/`) is available but not used for queries — the Neon serverless driver is used directly because it works in Cloudflare Workers.

### Server-first, No Client State
Public pages are fully server-rendered. `export const dynamic = "force-dynamic"` is set on public pages to prevent caching. The only client components are `AnalyticsBeacon` (fires events) and `EventLink` (wraps anchor clicks). No client-side state management library.

### Server Actions for Admin Mutations
Admin forms POST to Server Actions (`"use server"` functions in `app/admin/*/actions.ts`) rather than API routes. After mutation, actions `redirect()` back with a `?status=` query param for feedback messages. API routes are used for programmatic/JSON access.

### Styling Approach
- Tailwind CSS v4 utility classes for layout
- Global CSS custom properties (defined in `app/globals.css`) for brand tokens (`--accent`, `--muted`, `--shadow`, etc.)
- Admin UI uses semantic CSS classes (`.admin-panel`, `.admin-cta-primary`, `.admin-input`, etc.) defined in `globals.css` — NOT Tailwind utilities for component-level styles
- Brand theme is applied as inline `style` on `<main>` with `--brand-primary/secondary/background`, and all other color tokens derive from these three via `color-mix()`

### Authentication Invariant
Login always validates against `process.env.ADMIN_EMAIL` / `ADMIN_PASSWORD`. The `AdminUser` table in the DB is never read during authentication. This is a documented constraint in `ARCHITECTURE.md` and `lib/auth.ts`.

### Naming Conventions
- Files: `kebab-case.tsx` for components and pages, `kebab-case.ts` for utilities
- TypeScript: PascalCase types/interfaces, camelCase functions and variables
- DB columns: camelCase in Prisma schema (maps to quoted camelCase in Postgres)
- API routes: REST-style under `/api/admin/` for admin, `/api/public/` for public read, `/api/events` for analytics

### Architecture Risk to Track
The application uses `@neondatabase/serverless` Pool directly rather than the Prisma ORM client, because Cloudflare Workers cannot open TCP connections. This means type safety from Prisma's generated client is not enforced on query results — row types are declared manually as TypeScript types in each data file. Schema drift between `prisma/schema.prisma` and the hand-written SQL queries is a latent risk.
